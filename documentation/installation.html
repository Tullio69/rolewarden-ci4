Documentation

Installation

RoleWarden comes as three zips. Pick the one that matches where you start.

ZipFor
rolewarden-app-x.y.z.zipStarting from nothing, or without Composer: CodeIgniter 4, Shield, CodeIgniter's translations and RoleWarden, with vendor/ included and everything wired.
rolewarden-module-x.y.z.zipAn existing CodeIgniter 4 application with Shield, with or without Composer. The setup wizard adds RoleWarden to it from the browser.
rolewarden-demo-x.y.z.zipThe demo app on its own (the complete application already contains it).

The complete application

  1. Upload the content of the zip to your server.
  2. Point the web server's document root at the public/ folder. Everything else must stay outside the document root.
  3. Make writable/ writable by the web server, and the application's root folder too if you want the installer to write .env for you.
  4. Create an empty MySQL or MariaDB database and a user for it.
  5. Open the site. The home page leads to the installer.

The browser installer

/rolewarden/install takes the application from an empty database to a first super admin.

  1. Requirements. PHP version, extensions, a writable writable/, and whether .env can be written.
  2. Setup code. The installer saves a one-time code in writable/rolewarden/install-code.txt on the first visit. Open that file on the server (over FTP, for example) and type the code. Only someone who can read the server's files can install, so a stranger who finds a fresh upload first cannot make themselves super admin.
  3. Database. The application's address, then server, port, database name, user and password. The connection is tested; the settings go to .env together with a new encryption key. An existing key is kept, and so is an existing CI_ENVIRONMENT; otherwise it is set to production. When .env cannot be written, the installer shows its content to save by hand. A failed connection never shows database details on screen: they go to writable/logs/.
  4. Tables. The tables of CodeIgniter's Settings library, Shield and RoleWarden, and the system roles.
  5. First super admin. Username, email and password, checked with Shield's password rules. The account is created through Shield and is active.

Then the installer writes writable/rolewarden/installed.lock, deletes the setup code and refuses to run again. It also refuses on an application that already has an active super admin. It never contacts anything outside your server.

Last step: give the application a sender for its security emails, in .env:

email.fromEmail = 'noreply@example.com'
email.fromName = 'Example'
email.protocol = 'smtp'
email.SMTPHost = 'smtp.example.com'
email.SMTPUser = 'noreply@example.com'
email.SMTPPass = 'your-smtp-password'
email.SMTPPort = 587
email.SMTPCrypto = 'tls'

Without email.fromEmail the emails are skipped and a line is written to the log.

Addresses without index.php

CodeIgniter puts index.php/ in the addresses it builds, such as /index.php/rolewarden/users. When the web server sends every request to public/index.php (Apache with mod_rewrite and CodeIgniter's public/.htaccess, or nginx with try_files $uri $uri/ /index.php?$query_string;), add app.indexPage = '' to .env for shorter addresses. Without rewriting, leave it as it is.

Updating the complete application

RoleWarden lives in modules/rolewarden and is loaded from there by app/Config/Autoload.php. To update, replace that folder with the one from the new module zip, then run:

php spark migrate -n RoleWarden

The module in an existing application

For a CodeIgniter 4 application that already has Shield, its users and its own groups. There are two ways to add RoleWarden to it:

  • The setup wizard, /rolewarden/setup (recommended). A page in the browser asks a few questions, shows every change before making it, then runs the migrations, turns your groups into roles, makes a super admin and edits your configuration files, with a backup of each one. Steps 1 to 5 below.
  • By hand, if you prefer to edit the files yourself: see Without the wizard.

Before you start

  • Shield is installed and set up (php spark shield:setup), and signing in works.
  • PHP 8.3 or later. The wizard checks the rest of the requirements itself.
  • writable/ is writable by the web server. The wizard keeps its setup code and its answers in writable/rolewarden/.
  • For the wizard to edit your configuration, app/Config/Filters.php, app/Config/Routes.php and app/Config/Auth.php must be writable by the web server. If they are not, the wizard shows the exact text to paste by hand, so this is a convenience, not a requirement.
  • A backup of the database. The wizard runs migrations on it, and an application already in use deserves a copy first.

Step 1: load the module

Choose one of the two ways. Both are run from the root folder of your application, the one that contains spark, not from inside the module.

Without Composer. Unzip rolewarden-module-x.y.z.zip into a modules folder at the root of your application. The zip already contains a rolewarden folder, so you get modules/rolewarden/src/…. Check that modules/rolewarden/src/Config/Routes.php exists: some unzip tools, such as Windows' "Extract all", add one more folder level. Then add one line to $psr4 in app/Config/Autoload.php:

public $psr4 = [
    APP_NAMESPACE => APPPATH,
    'RoleWarden'  => ROOTPATH . 'modules/rolewarden/src',
];

With Composer. Unzip the module in the same place, add a path repository to your application's composer.json (not the module's), and require it:

"repositories": [
    { "type": "path", "url": "modules/rolewarden", "options": { "symlink": false } }
],
composer require rolewarden/codeigniter4-rolewarden

On Windows, leave out a version constraint such as :^1.2, or put it in double quotes: the command prompt removes the ^.

Optionally, for CodeIgniter's own messages (validation errors, dates) in Italian and other languages:

composer require codeigniter4/translations

Nothing else is needed before the wizard: its route is in the module's own src/Config/Routes.php, which CodeIgniter's route discovery finds by itself as long as app/Config/Modules.php keeps discovery on, the default. To check, the wizard's route must be listed:

php spark routes | grep rolewarden/setup

Step 2: open the wizard

Open /rolewarden/setup in the browser, for example https://example.com/rolewarden/setup. On the first visit the wizard saves a one-time setup code in writable/rolewarden/install-code.txt: open that file on the server and type the code. Only someone who can read the server's files can go on, even when someone is already signed in.

If you land on your sign-in page. Many applications apply Shield's session filter to every page in app/Config/Filters.php. Until the wizard has added its own exception, such an application sends a visitor of /rolewarden/setup to its sign-in page. Sign in with any account, open /rolewarden/setup again and type the code.

Every step before the last only asks and shows previews: nothing is written to the database, to your files or to the settings. The answers are kept in writable/rolewarden/install-manifest.json, so a closed browser or an expired session resumes at the first unanswered question, after the setup code again. The wizard speaks English and Italian: the language menu is at the top of every step.

Step 3: answer the questions

StepWhat it asks or showsWhat to choose
Setup codeThe code from writable/rolewarden/install-code.txt.Copy it without spaces.

The panel still requires signing in: the exceptions only let its stylesheets and the wizard through.
RolesYour groups from AuthGroups, with their users and permissions, and two options.Adapt the roles already here or Import RoleWarden's roles: see below. With Adapt, also who will manage the panel: the role that receives the panel's permissions, usually your administrators' group.

Super adminThe account that can do everything in RoleWarden, whatever its roles.An existing active user, or a new user, checked with your application's username, email and password rules. A new password is never saved in clear: only Shield's hash is kept until the account exists.
Who sees RoleWardenWhether RoleWarden's sign-in screen, profile and sessions pages are for everyone.Only administrators for an application already in use: your sign-in screen stays as it is, and profile and sessions open only for users with a permission of the panel. All users gives everyone RoleWarden's sign-in screen, profile and sessions.

Adapt or Import? Adapt keeps your groups as RoleWarden roles, with their users and permissions, and adds only super-admin: your code that calls $user->can() or inGroup() keeps working as before. Import adds RoleWarden's super-admin, admin and user next to your groups. The wizard suggests Import when AuthGroups has no groups or only Shield's stock ones (superadmin, admin, developer, user, beta), and Adapt otherwise. Adapt is refused for a group called super-admin, or called like a system role already in the database (an earlier php spark migrate creates admin and user): choose Import for it.

Permissions given to single users in Shield (the auth_permissions_users table) are not imported. The Roles step and the summary count them: give those users a role, or a user override from the panel, after the wizard.

Step 4: confirm and apply

Confirm and apply shows every answer and the exact change to each file. Only this step writes, in this order:

  1. Tables: the migrations of CodeIgniter's Settings library, Shield and RoleWarden.
  2. Roles: your groups adapted or imported, with their users and permissions.
  3. Super admin: the chosen user receives the role, or the new account is created.
  4. Filter exception in app/Config/Filters.php.
  5. Wiring: app/Config/Routes.php gets \RoleWarden\Config\RouteRegistrar::register($routes);, and only once that line is there app/Config/Auth.php gets RoleWarden's user provider (plus the sign-in view and redirect with All users).

Nothing is written into a configuration file that could break your application before the tables exist. Only Shield's own UserModel is replaced as user provider: if $userProvider names a model of your application, the wizard leaves it and asks you to make that model extend \RoleWarden\Models\UserModel.

Every file the wizard changes is protected:

  • the new content is parsed before writing, and content that does not parse is never written;
  • the original is saved next to it as <file>.rolewarden-bak, at the first write and never overwritten;
  • the file is written through a temporary file renamed over the original, so it is never half written;
  • where the server can run it, php -l checks the result, and a file it rejects is put back;
  • install-manifest.json records the path, the content before and after, and the date.

Once applying has started the answers are locked: the wizard can only continue or retry. The super admin alone can still be chosen again until its own step is done.

If a file cannot be changed

When a file is not writable, is missing, or is written in a shape the wizard does not recognise, the step stops at that file and shows the exact text to paste and where. Make the change in your editor, then choose I edited the files, continue: the wizard checks the file again and goes on. Steps already done are not repeated.

If the wizard stops

When a step fails for any other reason, the screen names the step and the details go to writable/logs/, never to the page. Fix the cause and apply again: the wizard resumes from the step that stopped.

  • Before any step has been applied, deleting writable/rolewarden/install-manifest.json starts the questions over.
  • Once a step is done, do not delete it. It records what was applied and which files were changed; without it the wizard would ask everything again and could apply different answers on top of what is done. To finish by hand instead, follow Without the wizard and compare each changed file with its .rolewarden-bak.

Step 5: after the wizard

The last page lists the files that were changed. The setup code is deleted and /rolewarden/setup answers 403 from now on.

  1. Sign out and in again, so that your session uses RoleWarden's user provider.
  2. Open /rolewarden with the super admin, and add a link to it in your application's menu.
  3. Give the application a sender for its security emails in .env (see the browser installer for the settings). Without it the emails are skipped and a line goes to the log.
  4. Check one user of each role in your application: the permissions now come from RoleWarden's tables, and $user->can() answers from there.

Version control. Commit modules/rolewarden (without Composer), the line in Autoload.php and the three changed configuration files. Keep the backups and the wizard's record out of the repository, but do not delete the record from the server:

# .gitignore
*.rolewarden-bak
/writable/rolewarden/

Changing your answers later. The wizard runs once. The role for new sign-ups and who opens the profile and sessions pages are both in /rolewarden/settings; roles, permissions and the super admin's assignments are in the panel. To move to RoleWarden's sign-in screen later, add the view and redirect to app/Config/Auth.php as in Wiring by hand.

Without the wizard

Load the module as in Step 1, then make the wiring and run the migrations yourself, in this order: tables first, wiring last. Wired before its tables exist, RoleWarden would stop every sign-in with a database error.

Tables by hand

Run the migrations in separate steps, so that RoleWarden gets a batch of its own and can be rolled back without Shield:

php spark migrate -n 'CodeIgniter\Settings'
php spark migrate -n 'CodeIgniter\Shield'
php spark migrate -n RoleWarden
php spark db:seed 'RoleWarden\Database\Seeds\RoleWardenSeeder'

By hand, the first super admin is a Shield user given the super-admin role once:

php spark shield:user create -n admin -e you@example.com
php spark shield:user activate -e you@example.com
INSERT INTO acl_user_roles (user_id, role_id)
SELECT i.user_id, r.id
FROM auth_identities i
JOIN acl_roles r ON r.slug = 'super-admin'
WHERE i.type = 'email_password' AND i.secret = 'you@example.com';

Replace acl_ if you changed the table prefix (see Configuration).

Wiring by hand

In app/Config/Auth.php, let Shield ask RoleWarden for permissions:

public string $userProvider = \RoleWarden\Models\UserModel::class;

In the same file, to use RoleWarden's sign-in screen (the $views array) and land people on the panel after signing in (the $redirects array). /rolewarden is the dashboard; whoever holds none of its dashboard.* permissions goes on to the first screen they can see:

'login' => '\RoleWarden\Views\auth\login',
'login' => 'rolewarden',

In app/Config/Routes.php, next to the line Shield already needs:

service('auth')->routes($routes);
\RoleWarden\Config\RouteRegistrar::register($routes);

That registers the panel, the installer, and a route serving the panel's CSS and JavaScript from the module: nothing is copied under public/. The module's events (session tracking, security emails, the registration hook) load by themselves as long as app/Config/Modules.php keeps module discovery on for events, the default.

If app/Config/Filters.php applies session (or group, permission) to every page, add RoleWarden's stylesheets to its exceptions, or the sign-in screen and the panel show without style:

'session' => ['except' => ['login*', 'register', 'auth/a/*', 'logout', 'rolewarden/assets/*', 'rolewarden/theme.css']],

Enable CSRF protection for every form in the same file (the panel's own routes have it in any case):

public array $globals = [
    'before' => [
        'csrf',
    ],
    // ...
];

Updating the module

Replace the module's folder (or run composer update rolewarden/codeigniter4-rolewarden), then php spark migrate -n RoleWarden. A new version brings its changes to existing data as migrations: for example, a new screen comes with a migration that gives the admin role its new permissions.

Removing the module

Roles and permissions live in RoleWarden's tables, so removing them takes them away. Users who registered or changed role after the installation have no group in Shield's auth_groups_users table: give them one before removing, or they sign in with no permissions.

  1. Unwire first, so that the application does not look for tables that are about to go: put back each file the wizard changed from its .rolewarden-bak (or remove the lines from Wiring by hand).
  2. Roll back the tables. migrate:rollback undoes whole batches, whatever the namespace. Look up RoleWarden's batch in the migrations table and roll back to the batch before it: 
    php spark migrate:rollback -b <previous batch>
    -b 0 rolls back everything, Shield included. The wizard runs each namespace in a batch of its own, so RoleWarden's is the last one it added.
  3. Remove the module. With Composer, composer remove rolewarden/codeigniter4-rolewarden (deleting the folder by hand leaves Composer's link to it behind); without Composer, remove the line from app/Config/Autoload.php. Then delete modules/rolewarden and writable/rolewarden/.

In a subfolder or behind a proxy

In a subfolder

The application can live at an address such as https://example.com/admin/. Point that address at the public/ folder (an alias or a symbolic link) and set app.baseURL in .env to the full address with the subfolder and a final slash. The installer writes it from the address it was opened at. Every link, form and email of the panel is built from app.baseURL.

Behind a reverse proxy or a load balancer

Behind a proxy every request comes from the proxy's own address unless CodeIgniter is told to trust it. The sign-in limit per IP address would then count everyone together and lock everyone out at once, and the activity log, the sessions list and the security emails would show the proxy's address. List your proxies in app/Config/App.php, with the header that carries the visitor's address:

public array $proxyIPs = [
    '10.0.0.5'     => 'X-Forwarded-For',
    '172.16.0.0/12' => 'X-Forwarded-For',
];

When the proxy handles HTTPS and talks to the application over plain HTTP, it must also send X-Forwarded-Proto: https. CodeIgniter reads that header only from the proxies in $proxyIPs. Keep app.baseURL on https://.

The proxy visitors connect to must replace X-Forwarded-For with the visitor's address, not add to what the visitor sent: otherwise anyone can write an address of their choice in the header and get round the sign-in limit per IP address. On nginx:

proxy_set_header Host $host;
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;

On any site served over HTTPS, with a proxy or without, add cookie.secure = true to .env so that the session and "Remember me" cookies are never sent over plain HTTP.

The demo app

A small document register with three roles in a chain of inheritance: a Reader only reads, an Author writes and edits their own documents, an Approver approves and deletes. It shows the permissions at work and is the model to copy for your own screens. The complete application contains it in modules/rolewarden-demo, not installed.

php spark demo:install     # table, permissions, roles, three accounts, sample documents
php spark demo:uninstall   # removes all of it, and nothing else

The accounts are reader@example.com, author@example.com and approver@example.com, with the password set in .env as demo.password (or generated and printed once). Open /demo. In your own application, copy the demo folder and add one line to $psr4 in app/Config/Autoload.php and one to app/Config/Routes.php, as its README.md explains.

Showcase mode, for a public demo or a product video, adds a bar that switches the session between the three demo accounts without a password: demo.showcase = true in .env. It only switches to the accounts the demo created, and it is ignored when CI_ENVIRONMENT is production.
